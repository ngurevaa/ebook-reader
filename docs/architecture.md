# Архитектура проекта

EBook Reader использует модульную архитектуру на основе **Clean Architecture** и **MVI** в presentation-слое.

Проект разделён на общие модули `core` и функциональные модули `feature`. Каждый feature разделён на два Gradle-модуля — `api` и `impl`. Такое разделение позволяет отделить публичный контракт функциональности от её внутренней реализации.

## Структура проекта

```text
app
│
├── core
│   ├── database
│   ├── designsystem
│   ├── network
│   ├── ui
│   └── util
│
└── feature
    ├── auth
    │   ├── api
    │   └── impl
    │
    ├── booklist
    │   ├── api
    │   └── impl
    │
    ├── bookupload
    │   ├── api
    │   └── impl
    │
    ├── profile
    │   ├── api
    │   └── impl
    │
    └── reader
        ├── api
        └── impl
```

---

## Модуль `app`

`app` является точкой сборки Android-приложения.

Он объединяет функциональные модули и общие модули `core`, содержит конфигурацию приложения и отвечает за его запуск.

Бизнес-логика функциональных областей располагается в соответствующих `feature`-модулях.

---

# Core-модули

`core` содержит общую функциональность и инфраструктуру, используемую несколькими feature-модулями.

## `core:database`

Содержит компоненты для работы с локальными данными.

Модуль используется для хранения данных, которые должны быть доступны без обращения к удалённым сервисам, в том числе для локального хранения загруженных книг.

## `core:network`

Содержит общую инфраструктуру для взаимодействия с внешними сервисами.

В проекте используются:

* Firebase Authentication;
* Firebase Firestore;
* Supabase Storage.

Детали работы с конкретными сервисами используются на уровне соответствующих feature и не должны распространяться на остальные части приложения без необходимости.

## `core:designsystem`

Содержит общие элементы визуального оформления приложения:

* цветовые схемы;
* типографику;
* темы;
* переиспользуемые элементы дизайна.

## `core:ui`

Содержит переиспользуемые UI-компоненты, необходимые нескольким feature-модулям.

Компоненты, специфичные только для одного feature, остаются внутри его `impl`-модуля.

## `core:util`

Содержит общие вспомогательные классы и функции, не относящиеся к конкретной функциональной области приложения.

---

# Feature-модули

Каждая основная функциональная область приложения выделена в отдельный feature:

| Модуль               | Назначение                                  |
| -------------------- | ------------------------------------------- |
| `feature:auth`       | регистрация и авторизация пользователя      |
| `feature:booklist`   | отображение и управление списком книг       |
| `feature:bookupload` | загрузка книг                               |
| `feature:profile`    | просмотр и редактирование профиля           |
| `feature:reader`     | чтение книг и управление параметрами чтения |

Разделение на feature позволяет изолировать функциональные области и уменьшить связанность между ними.

---

# Разделение `api` и `impl`

Каждый feature состоит из двух Gradle-модулей:

```text
feature:<name>
├── api
└── impl
```

## `api`

`api` содержит публичный контракт feature.

Он предоставляет другим модулям только те компоненты, которые необходимы для взаимодействия с данной функциональностью.

Внутренние детали реализации feature в `api` не публикуются.

## `impl`

`impl` содержит внутреннюю реализацию feature.

В зависимости от конкретного feature здесь располагаются:

* Compose UI;
* ViewModel;
* состояние и обработка событий;
* use case;
* контракты repository в Domain;
* реализации repository в Data;
* источники данных;
* преобразование данных;
* другая внутренняя логика feature.

Таким образом, `api` определяет публичный контракт, а `impl` содержит его реализацию.

Зависимость между модулями имеет направление:

```text
feature:<name>:impl
          │
          ▼
feature:<name>:api
```

Взаимодействие других feature с функциональностью осуществляется через публичный `api`, а не через внутренние компоненты `impl`.

---

# Clean Architecture

Внутри feature используется разделение на три слоя:

```text
┌─────────────────────────────┐
│        Presentation         │
│                             │
│ Compose UI                  │
│ ViewModel                   │
│ State / Events              │
└──────────────┬──────────────┘
               │
               ▼
┌─────────────────────────────┐
│           Domain            │
│                             │
│ Use Cases                   │
│ Repository interfaces       │
│ Domain models               │
└──────────────┬──────────────┘
               ▲
               │ implements
               │
┌──────────────┴──────────────┐
│            Data             │
│                             │
│ Repository implementations  │
│ Data Sources                │
│ Data models                 │
│ Mappers                     │
└─────────────────────────────┘
```

Главный принцип заключается в том, что **Domain определяет контракты, а Data предоставляет их реализации**.

Поэтому бизнес-логика не зависит от конкретного способа хранения или получения данных.

---

## Presentation

Presentation-слой отвечает за взаимодействие с пользователем и отображение состояния приложения.

В него входят:

* Jetpack Compose UI;
* ViewModel;
* состояние экрана;
* обработка пользовательских событий.

UI передаёт события во ViewModel. ViewModel запускает необходимые операции и обновляет состояние, которое наблюдает Compose UI.

---

## Domain

Domain-слой содержит бизнес-логику, не зависящую от конкретных технологий хранения данных или внешних сервисов.

Основные компоненты:

* use case;
* интерфейсы repository;
* доменные модели.

Use case используют интерфейсы repository, определённые в Domain.

Например, операции с книгами могут быть представлены отдельными use case:

* загрузка книги;
* получение списка книг;
* поиск книги;
* скачивание книги;
* удаление книги;
* сохранение позиции чтения.

Domain не знает, откуда фактически поступают данные — из локального хранилища, Firebase или Supabase.

---

## Data

Data-слой отвечает за получение, сохранение и преобразование данных.

Он содержит:

* реализации repository;
* источники данных;
* модели данных;
* преобразование данных между слоями.

Repository implementation реализует интерфейс, определённый в Domain, и скрывает от него детали взаимодействия с конкретными источниками данных.

Например, реализация repository может использовать локальное хранилище, Firebase или Supabase в зависимости от операции.

---

# Направление зависимостей

Зависимости внутри feature направлены от внешних слоёв к абстракциям Domain:

```text
Presentation
     │
     ▼
  Use Case
     │
     ▼
Repository interface
     ▲
     │
     │ implements
     │
Repository implementation
     │
     ▼
Data Source
```

При этом Domain не зависит от Data.

Это позволяет заменить конкретную реализацию хранения или получения данных без изменения бизнес-логики.

На уровне модулей общая схема выглядит следующим образом:

```text
                    ┌───────────┐
                    │    app    │
                    └─────┬─────┘
                          │
             ┌────────────┴────────────┐
             │                         │
             ▼                         ▼
       Feature-модули             Core-модули
       ├── auth                   ├── database
       ├── booklist               ├── designsystem
       ├── bookupload              ├── network
       ├── profile                ├── ui
       └── reader                 └── util
```

Feature-модули не должны зависеть от внутренних деталей реализации других feature. Для взаимодействия между функциональными областями используется публичный `api` соответствующего feature.

Общая функциональность выносится в `core`, если она используется несколькими feature-модулями.

# Управление состоянием

Для реализации MVI используется **Orbit MVI**.

Основной поток взаимодействия:

```text
┌──────────────┐
│ Пользователь │
└──────┬───────┘
       │
       ▼
┌──────────────┐
│  UI Event    │
└──────┬───────┘
       │
       ▼
┌──────────────┐
│  ViewModel   │
│  Orbit MVI   │
└──────┬───────┘
       │
       ▼
┌──────────────┐
│   Use Case   │
└──────┬───────┘
       │
       ▼
┌──────────────┐
│  Repository  │
└──────┬───────┘
       │
       ▼
┌──────────────┐
│ Data Source  │
└──────┬───────┘
       │
       ▼
     Result
       │
       ▼
┌──────────────┐
│  ViewModel   │
└──────┬───────┘
       │
       ▼
┌──────────────┐
│    State     │
└──────┬───────┘
       │
       ▼
┌──────────────┐
│ Compose UI   │
└──────────────┘
```

UI не изменяет состояние приложения напрямую. Пользовательские действия передаются во ViewModel, которая выполняет необходимую операцию и обновляет состояние.

---

# Работа с данными

В приложении используются следующие источники данных:

| Источник                | Назначение                                   |
| ----------------------- | -------------------------------------------- |
| Firebase Authentication | регистрация и авторизация пользователей      |
| Firebase Firestore      | хранение метаданных книг                     |
| Supabase Storage        | хранение файлов книг и изображений профиля   |
| Room                    | хранение загруженных книг и локальных данных |
| SharedPreferences       | сохранение позиции чтения и настроек         |

Firebase Firestore хранит метаданные книг, а сами файлы книг хранятся в Supabase Storage.

---

# Dependency Injection

Для внедрения зависимостей используется **Koin**.

Koin используется для создания и предоставления зависимостей, включая:

* ViewModel;
* use case;
* repository;
* источники данных;
* клиенты внешних сервисов.

Создание объектов отделено от их использования, что позволяет управлять зависимостями и заменять конкретные реализации.

---

# Основные архитектурные принципы

В проекте используются следующие принципы:

* разделение приложения на независимые функциональные модули;
* разделение публичного API и внутренней реализации feature;
* разделение Presentation, Domain и Data;
* Dependency Inversion;
* однонаправленный поток данных;
* минимизация связанности между feature-модулями;
* вынесение общей функциональности в `core`;
* сокрытие деталей реализации за интерфейсами;
* Dependency Injection.

Такая структура позволяет изолировать функциональные области, ограничивать связанность между модулями и изменять конкретные реализации без изменения бизнес-логики и публичных контрактов.
