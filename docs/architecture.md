# Архитектура проекта EBook Reader

## 1. Общая архитектура

EBook Reader построен на основе **Clean Architecture** и архитектурного паттерна **MVI (Model–View–Intent)**.

Архитектура разделена на:

* `app` — точка входа приложения и сборка всех модулей;
* `core` — общие компоненты и инфраструктура;
* `feature` — функциональные модули приложения.

Функциональные возможности разделены по отдельным feature-модулям, а внутри каждого feature используется разделение на `api` и `impl`.

Основная зависимость между слоями направлена от реализации к абстракциям:

```text
Presentation
     ↓
UseCase
     ↓
Repository interface
     ↓
Repository implementation
     ↓
DataSource / external services
```

Это позволяет отделить бизнес-логику от деталей хранения данных, сетевых сервисов и пользовательского интерфейса.

---

## 2. Структура модулей

```text
app/
│
├── core/
│   ├── database/
│   ├── designsystem/
│   ├── network/
│   ├── ui/
│   └── util/
│
└── feature/
    ├── auth/
    │   ├── api/
    │   └── impl/
    │
    ├── booklist/
    │   ├── api/
    │   └── impl/
    │
    ├── bookupload/
    │   ├── api/
    │   └── impl/
    │
    ├── profile/
    │   ├── api/
    │   └── impl/
    │
    └── reader/
        ├── api/
        └── impl/
```

### `app`

Модуль приложения является точкой сборки всех остальных модулей.

В нём находятся:

* `MainActivity`;
* настройка темы приложения;
* создание корневого UI;
* навигация между feature;
* подключение feature-модулей.

`app` зависит от необходимых `core` и `feature` модулей.

---

# 3. Core-модули

## 3.1 `core:database`

Модуль отвечает за локальное хранение структурированных данных приложения.

Для работы с базой данных используется **Room**.

Основные компоненты:

* `AppDatabase` — экземпляр базы данных;
* `BookDao` — интерфейс доступа к таблице книг;
* `BookEntity` — сущность книги;
* `DateConverter` — конвертация типов даты для Room.

Пример структуры:

```text
core/database/
└── AppDatabase
    └── BookDao
        └── BookEntity
```

`BookDao` предоставляет операции для:

* получения списка книг;
* добавления книг;
* обновления книг;
* удаления отсутствующих записей;
* изменения признака локального наличия книги.

Список книг предоставляется через `Flow`, поэтому изменения базы данных автоматически передаются в соответствующие компоненты приложения.

---

## 3.2 `core:network`

Модуль содержит общую сетевую инфраструктуру, используемую приложением.

В текущей реализации здесь настраивается клиент **Supabase**.

Firebase при этом не вынесен полностью в `core:network`: соответствующие Firebase API используются непосредственно в feature-модулях, где они необходимы.

---

## 3.3 `core:designsystem`

Модуль содержит общие элементы визуального оформления приложения:

* Material 3 theme;
* цветовые схемы;
* типографику;
* общие настройки интерфейса;
* переиспользуемые элементы дизайна.

Централизация визуальных компонентов позволяет использовать единый стиль во всех feature-модулях.

---

## 3.4 `core:ui`

Модуль содержит переиспользуемые UI-компоненты, которые используются несколькими feature.

Компоненты этого модуля не должны содержать бизнес-логику конкретного функционального модуля.

---

## 3.5 `core:util`

Модуль содержит общие вспомогательные компоненты приложения.

В нём находятся:

* утилиты работы с файлами;
* валидация;
* работа с ресурсами;
* вспомогательные функции, используемые несколькими модулями.

---

# 4. Feature-модули

Каждая функциональная область приложения выделена в отдельный feature:

```text
auth
booklist
bookupload
profile
reader
```

Каждый feature разделён на два Gradle-модуля:

```text
feature/<feature-name>/
├── api/
└── impl/
```

## 4.1 `api`

Модуль `api` содержит публичные контракты feature.

В зависимости от конкретного feature здесь находятся:

* domain-модели;
* интерфейсы Repository;
* интерфейсы UseCase;
* navigation routes;
* другие контракты, необходимые для взаимодействия с feature.

Например:

```text
api/
├── domain/
│   ├── model/
│   ├── repository/
│   └── usecase/
└── navigation/
```

Главная задача `api` — предоставить абстракции, не раскрывая детали реализации функциональности.

---

## 4.2 `impl`

Модуль `impl` содержит реализацию feature.

В нём находятся:

* Compose UI;
* ViewModel;
* MVI state;
* MVI event;
* реализация UseCase;
* реализация Repository;
* DataSource;
* Mapper;
* Dependency Injection;
* Worker, если он относится к конкретному feature.

Таким образом, `impl` знает о деталях реализации, а `api` содержит контракты, которыми могут пользоваться другие модули.

---

# 5. Presentation Layer

Для организации состояния пользовательского интерфейса используется **MVI**.

Основные элементы:

```text
Intent/Event
     ↓
ViewModel
     ↓
UseCase
     ↓
Repository
     ↓
State
     ↓
UI
```

### Event

Представляет действие пользователя или системы.

Например:

* нажатие кнопки;
* изменение поискового запроса;
* удаление книги;
* изменение настроек чтения.

### State

Содержит текущее состояние экрана.

UI подписывается на состояние и отображает его.

### ViewModel

ViewModel:

* принимает события;
* вызывает соответствующие UseCase;
* изменяет состояние;
* обрабатывает результат выполнения операций.

UI не взаимодействует непосредственно с Repository или внешними сервисами.

---

# 6. Domain Layer

Domain-часть feature содержит бизнес-контракты приложения.

Основными компонентами являются:

### Domain Model

Представляет данные предметной области.

Например, книга описывается моделью, которая используется бизнес-логикой независимо от способа её хранения.

### Repository

Repository является абстракцией источника данных.

Например:

```kotlin
interface BookRepository {
    ...
}
```

Интерфейс Repository находится в `api`, а его реализация — в `impl`.

Это позволяет бизнес-логике не зависеть напрямую от Room, Firebase или Supabase.

### UseCase

UseCase представляет отдельную бизнес-операцию.

Например:

* загрузка книг;
* удаление книги;
* загрузка книги;
* получение профиля;
* обновление данных профиля.

Интерфейс UseCase относится к публичному контракту feature, а его реализация находится в `impl`.

---

# 7. Data Layer

Data-часть отвечает за получение и сохранение данных.

В зависимости от feature используются различные источники данных:

```text
                   ┌── Room
                   │
Repository ────────┼── Firebase
                   │
                   ├── Supabase
                   │
                   └── Local files
```

Repository скрывает детали работы с конкретными источниками.

Например, работа с книгами может включать:

1. получение метаданных книги из Firestore;
2. получение файла книги из Supabase Storage;
3. сохранение файла в локальное хранилище;
4. сохранение локальных метаданных в Room.

---

# 8. Хранение данных

В приложении используется несколько типов хранилищ.

## Room

Room используется для локального хранения метаданных книг.

В базе хранятся данные, необходимые для отображения списка книг и отслеживания их локального наличия.

```text
Room
  ↓
BookDao
  ↓
BookRepository
  ↓
UseCase
  ↓
ViewModel
  ↓
UI
```

## SharedPreferences

`SharedPreferences` используется для хранения прогресса чтения.

Для каждой книги используется отдельный ключ:

```text
progress_<fileName>
```

При открытии книги сохранённый прогресс считывается и используется для восстановления позиции чтения.

## Локальная файловая система

Файлы книг хранятся в директории приложения:

```text
filesDir/books/
```

В локальном хранилище могут находиться файлы форматов:

* TXT;
* EPUB;
* PDF.

---

# 9. Работа с Firebase

В проекте используются:

* **Firebase Authentication** — регистрация и аутентификация пользователей;
* **Firebase Firestore** — хранение метаданных книг и данных профиля.

Firebase API используется в соответствующих feature-модулях.

Например, authentication feature взаимодействует с Firebase Authentication для:

```text
Registration
    ↓
Firebase Authentication

Login
    ↓
Firebase Authentication
```

Book и Profile feature используют Firebase Firestore для хранения связанных с пользователем данных.

---

# 10. Работа с Supabase

**Supabase Storage** используется для хранения файлов книг и изображений.

Общий поток работы с книгой:

```text
User
  ↓
Book Upload UI
  ↓
ViewModel
  ↓
Upload UseCase
  ↓
BookRepository
  ↓
Supabase Storage
```

Метаданные книги при этом сохраняются отдельно:

```text
Book metadata
     ↓
Firestore
```

Таким образом, файл книги и его метаданные хранятся независимо.

---

# 11. Загрузка книг в фоне

Для фоновой загрузки используется **WorkManager**.

Загрузка выполняется через `BookUploadWorker`.

Основной поток:

```text
User selects book
       ↓
Book Upload UI
       ↓
ViewModel
       ↓
Upload UseCase
       ↓
WorkManager
       ↓
BookUploadWorker
       ↓
Supabase Storage
       ↓
Firestore
```

Worker выполняется в foreground-режиме и показывает уведомление о процессе загрузки.

При ошибке `IOException` выполняется повторная попытка. Количество попыток ограничено тремя.

---

# 12. Чтение книг

Для чтения поддерживаются три формата:

```text
TXT
EPUB
PDF
```

Используются следующие библиотеки:

* TXT — стандартное чтение файлов;
* EPUB — Epublib;
* PDF — PDFBox Android.

Поскольку большие книги могут содержать большое количество текста, EPUB и PDF обрабатываются частями.

Общий поток:

```text
Local file
    ↓
LocalBookDataSource
    ↓
BookRepository
    ↓
Reader UseCase
    ↓
Reader ViewModel
    ↓
Reader UI
```

---

# 13. Синхронизация книг

Список книг хранится локально в Room и синхронизируется с удалёнными данными.

В локальной базе для книги хранится признак её наличия на устройстве.

При синхронизации:

```text
Remote data
    ↓
Firestore
    ↓
Repository
    ↓
Room
    ↓
Books list
```

Если файл книги был загружен на устройство, его наличие дополнительно отражается в локальных данных.

Физические файлы книг находятся в локальном файловом хранилище приложения.

---

# 14. Навигация

Навигация реализована с использованием **Navigation Compose**.

Feature предоставляет navigation routes через `api`, а конкретные экраны реализуются внутри `impl`.

Основные функциональные области:

```text
Auth
  ↓
Book List
  ├── Book Upload
  ├── Reader
  └── Profile
```

Такое разделение позволяет не связывать navigation напрямую с внутренней реализацией экранов feature.

---

# 15. Dependency Injection

Для Dependency Injection используется **Koin**.

Через Koin предоставляются зависимости:

* Repository;
* UseCase;
* DataSource;
* ViewModel;
* другие необходимые компоненты.

Например:

```text
ViewModel
    ↓
UseCase
    ↓
Repository
    ↓
DataSource
```

Каждая зависимость создаётся через DI и передаётся компоненту, которому она необходима.

Это уменьшает связанность компонентов и упрощает замену реализаций.

---

# 16. Зависимости между модулями

Общая схема зависимостей:

```text
                       app
                        │
          ┌─────────────┴─────────────┐
          ↓                           ↓
       feature                      core
          │                           │
     ┌────┴────┐              ┌───────┴────────┐
     ↓         ↓              ↓                ↓
    api       impl       database / ...   designsystem / ui
```

Внутри feature:

```text
impl
 │
 ├── depends on → api
 └── depends on → core
```

Другие feature взаимодействуют с feature через публичные контракты `api`, а не через детали реализации `impl`.

---

# 17. Принципы архитектуры

При построении проекта используются следующие принципы:

### Разделение ответственности

Каждый компонент отвечает за одну область:

* UI отображает состояние;
* ViewModel управляет состоянием экрана;
* UseCase выполняет бизнес-операцию;
* Repository абстрагирует источники данных;
* DataSource работает с конкретным хранилищем или сервисом.

### Dependency Inversion

Бизнес-логика зависит от интерфейсов Repository, а не от конкретных реализаций.

```text
Domain
  ↓
Repository interface
  ↑
Repository implementation
```

### Модульность

Функциональность разделена на независимые feature-модули.

Это позволяет:

* локализовать изменения;
* уменьшить связанность;
* разделить ответственность между функциональными областями;
* скрывать детали реализации feature.

### Переиспользование

Общие компоненты вынесены в `core`, чтобы не дублировать их в feature-модулях.

# 18. Итоговая схема

Общую архитектуру приложения можно представить следующим образом:

```text
                         EBook Reader
                              │
              ┌───────────────┴────────────────┐
              │                                │
             app                              core
              │                                │
       Navigation + UI          ┌───────────────┼───────────────┐
                                │               │               │
                           database        network        designsystem
                                │               │               │
                               Room          Supabase          UI
                                │
              ┌─────────────────┴─────────────────┐
              │                                   │
           feature                              feature
              │                                   │
          ┌───┴───┐                           ┌───┴───┐
          │       │                           │       │
         api     impl                        api     impl
          │       │                           │       │
      contracts  UI                       contracts  UI
                 │                                  │
            ViewModel                           ViewModel
                 │                                  │
              UseCase                             UseCase
                 │                                  │
            Repository                         Repository
                 │                                  │
        ┌────────┼────────┐                 ┌───────┼───────┐
        ↓        ↓        ↓                 ↓       ↓       ↓
       Room   Firebase Supabase           Local  Firebase Supabase
                                         files
```

Таким образом, приложение разделяет пользовательский интерфейс, бизнес-логику и работу с данными, а функциональные возможности изолированы в отдельных feature-модулях.
